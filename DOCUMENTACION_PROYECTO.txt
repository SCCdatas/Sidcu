DOCUMENTACION DEL PROYECTO SIDCU
Simulador Integral de Decisiones de Carrera Universitaria
Proyecto integrador desarrollado en CESDE

======================================================================
1. PRESENTACION Y OBJETIVOS
======================================================================

SIDCU es una aplicacion web para consultar carreras, habilidades y
universidades, y para apoyar la exploracion de intereses vocacionales.
El repositorio contiene un frontend web y un backend REST que persiste
catalogos y relaciones en PostgreSQL.

Objetivo general
----------------
Facilitar la exploracion y orientacion academica de estudiantes mediante
un catalogo de carreras, habilidades y universidades, y ofrecer una API
capaz de relacionar intereses academicos con la oferta universitaria.

Objetivos especificos
---------------------
1. Publicar y consultar carreras, niveles academicos, areas y habilidades.
2. Consultar universidades y las carreras que cada una ofrece.
3. Mantener registros de estudiantes, perfiles e intereses en el backend.
4. Recomendar universidades a partir de las carreras de interes de un
   estudiante, priorizando instituciones de su ciudad.
5. Presentar graficos descriptivos del catalogo academico consultando los
   datos actuales de la API.
6. Proporcionar paginas de exploracion, comparacion y autoevaluacion
   vocacional en el navegador.

El objetivo anterior resume el proposito que se desprende del codigo y
la documentacion del backend; no constituye una especificacion formal de
CESDE.

======================================================================
2. ARQUITECTURA Y FLUJO DE DATOS
======================================================================

Frontend:
- React 19, React Router 7 y Vite 8.
- Aplicacion de pagina unica (SPA) publicada como sitio estatico.
- Ruta de API configurable por VITE_API_URL. Si no se configura, usa
  https://sidcu-2.onrender.com.
- Las paginas de carreras, detalle de carrera, universidades y analitica
  consultan endpoints del backend.
- Las paginas de comparacion y las evaluaciones vocacionales usan datos
  o estado del navegador; no se deben interpretar como operaciones
  guardadas en la base de datos.

Backend:
- Java 17 y Spring Boot 4.
- API HTTP/JSON implementada con Spring MVC, servicios, repositorios
  Spring Data JPA y entidades Hibernate.
- PostgreSQL como almacenamiento.
- Swagger UI, OpenAPI y Scalar para explorar la API; Actuator ofrece
  comprobaciones de salud.

Flujo de una consulta de catalogo:
Navegador -> componente React -> frontend/src/services/api.js -> endpoint
REST -> controlador -> servicio/reglas de negocio -> repositorio JPA ->
PostgreSQL. La respuesta se transforma a DTO y se muestra en el frontend.

Despliegue:
- render.yaml define un servicio Docker para el backend y un sitio estatico
  para el frontend.
- El backend recibe DB_URL, DB_USERNAME y DB_PASSWORD como variables de
  entorno. No se incluyen credenciales en este documento.
- CORS se configura mediante CORS_ALLOWED_ORIGINS. La configuracion
  actual del manifiesto usa "*" y conviene restringirla al dominio real
  del frontend en una configuracion de produccion.
- El sitio estatico reescribe las rutas del navegador a index.html para
  que funcione React Router.

======================================================================
3. FUNCIONALIDADES Y LIMITES ACTUALES
======================================================================

Conectado a la API:
- Listado/busqueda local de carreras a partir del catalogo recibido.
- Detalle de una carrera del catalogo por identificador.
- Listado de universidades.
- Tab ANALITICA, que combina carreras, universidades, habilidades y
  relaciones de oferta para construir indicadores, respuestas y graficos.

Implementado en el backend:
- CRUD de carreras, habilidades, universidades, estudiantes y perfiles.
- Creacion, consulta y eliminacion de intereses de carrera e intereses
  universitarios.
- Creacion, consulta y eliminacion de relaciones universidad-carrera.
- Recomendacion de universidades para un estudiante.
- Validaciones y reglas de negocio documentadas en la seccion 5.

No asumir como conectado o persistente:
- El inicio de sesion valida una lista local de administradores y guarda
  el usuario en localStorage; no usa autenticacion de la API.
- La pantalla de registro es solo una interfaz, sin registro funcional.
- Los cuestionarios calculan resultados en el navegador y guardan el
  resultado en localStorage; no crean perfiles ni intereses en la base.
- La pagina Comparador usa el catalogo estatico CarrerasData.js.
- La analitica resume registros actuales del catalogo; no mide matriculas,
  demanda de estudiantes ni tendencias historicas.
- La interfaz no expone en este momento todo el CRUD de estudiantes,
  perfiles e intereses disponible en la API.

======================================================================
5. API REST Y REGLAS DE NEGOCIO
======================================================================

Rutas principales:
- /actuator/health: estado del servicio.
- /swagger-ui.html, /v3/api-docs y /scalar: documentacion de la API.
- /api/carreras: GET lista (filtros area/nivel), GET /{id}, POST, PUT
  /{id}, DELETE /{id}.
- /api/habilidades: GET lista, GET /{id}, POST, PUT /{id}, DELETE /{id}.
- /api/universidades: GET lista (filtros ciudad/nombre), GET /{id}, POST,
  PUT /{id}, DELETE /{id}.
- /api/estudiantes: GET lista (filtros documento/ciudad), GET /{id},
  POST, PUT /{id}, DELETE /{id}.
- /api/estudiantes/{id}/universidades-recomendadas: recomendaciones.
- /api/perfiles-estudiantes: GET lista (filtro estudianteId), GET /{id},
  POST, PUT /{id}, DELETE /{id}.
- /api/intereses: GET lista, POST, GET y DELETE
  /estudiantes/{estudianteId}/carreras/{carreraId}.
- /api/intereses-universidades: GET lista, POST, GET y DELETE
  /estudiantes/{estudianteId}/universidades/{universidadId}.
- /api/universidades-carreras: GET lista, POST, GET y DELETE
  /universidades/{universidadId}/carreras/{carreraId}.

Reglas principales implementadas por los servicios:
- Un estudiante puede tener como maximo cinco carreras de interes y no
  puede repetir la misma relacion.
- Solo se registra interes en una universidad si ofrece al menos una
  carrera que interese al estudiante.
- Una universidad no puede repetir la misma carrera en su oferta.
- Cada estudiante puede tener un unico perfil.
- Documento de estudiante, nombre de carrera, nombre de universidad y
  nombre de habilidad son unicos.
- No se permite eliminar carreras, universidades o habilidades que
  tengan relaciones que deban conservarse (oferta/intereses/asociaciones).
- La recomendacion busca universidades que ofrecen alguna carrera de
  interes y prioriza las ubicadas en la ciudad del estudiante.
- Recursos inexistentes generan respuesta HTTP 404. Las reglas de negocio
  incumplidas generan HTTP 409. Validaciones y errores inesperados se
  convierten en respuestas de error centralizadas.

La analitica del frontend consulta GET /api/carreras,
/api/universidades, /api/habilidades y /api/universidades-carreras.
Sus graficos describen el contenido de esos catalogos en el momento de
consulta, no actividad historica.

7. ARCHIVOS DEL BACKEND Y RESPONSABILIDAD DE SUS FUNCIONES
======================================================================

Arranque, configuracion y despliegue
------------------------------------
backend/src/main/java/com/cesde/sidcudb/SidcudbApplication.java
- SidcudbApplication.main(): inicia Spring Boot.

backend/src/main/java/com/cesde/sidcudb/config/CorsConfig.java
- CorsConfig(...): recibe los origenes CORS configurados.
- addCorsMappings(...): permite solicitudes CORS en los endpoints API.

backend/src/main/java/com/cesde/sidcudb/config/OpenApiConfig.java
- sidcuOpenAPI(): configura titulo y metadatos de OpenAPI.

backend/src/main/java/com/cesde/sidcudb/config/DataSeederConfig.java
- cargarDatosIniciales(...): crea datos de ejemplo cuando el seeder esta
  habilitado y los catalogos principales estan vacios.

  universidad(nombre, ciudad, tipo, direccion, codigoPostal) y
  estudiante(documento, nombre, ciudad): construyen las entidades de

- Configura nombre de aplicacion, datasource PostgreSQL desde entorno,

backend/.dockerignore
- Excluye del contexto Docker archivos locales, artefactos y secretos.

backend/.env.example
- Plantilla de nombres de variables requeridas; no debe contener valores
  reales de credenciales.

render.yaml
- Define el servicio Docker del backend, sus variables de entorno y health
  check, y el sitio estatico frontend con rewrite SPA.

Controladores: entrada HTTP y conversion a respuestas
-----------------------------------------------------
Los controladores reciben peticiones, validan DTO de entrada, llaman a su
servicio y definen los codigos de respuesta. Los metodos CRUD mencionados
son las funciones list(), buscarPorId(), crear(), actualizar() y
eliminar(), segun el recurso; las rutas exactas aparecen en la seccion 5.

backend/src/main/java/com/cesde/sidcudb/controller/CarreraController.java
- listar(): filtra/lista carreras; buscarPorId(): obtiene una carrera;
  crear(), actualizar() y eliminar(): administran ese recurso.

backend/src/main/java/com/cesde/sidcudb/controller/EstudianteController.java
- listar(), buscarPorId(), crear(), actualizar() y eliminar(): CRUD de
  estudiantes. recomendarUniversidades(): obtiene recomendaciones.

backend/src/main/java/com/cesde/sidcudb/controller/HabilidadController.java
- listar(), buscarPorId(), crear(), actualizar() y eliminar(): CRUD de
  habilidades.

backend/src/main/java/com/cesde/sidcudb/controller/UniversidadController.java
- listar(), buscarPorId(), crear(), actualizar() y eliminar(): CRUD de
  universidades.

backend/src/main/java/com/cesde/sidcudb/controller/PerfilEstudianteController.java
- listar(), buscarPorId(), crear(), actualizar() y eliminar(): CRUD de
  perfiles de estudiantes.

backend/src/main/java/com/cesde/sidcudb/controller/InteresController.java
- listar(), buscarPorId(), crear() y eliminar(): administra intereses
  entre estudiante y carrera.

backend/src/main/java/com/cesde/sidcudb/controller/InteresUniversidadController.java
- listar(), buscarPorId(), crear() y eliminar(): administra intereses
  entre estudiante y universidad.

backend/src/main/java/com/cesde/sidcudb/controller/UniversidadCarreraController.java
- listar(), buscarPorId(), crear() y eliminar(): administra la relacion
  entre universidad y carrera ofertada.

Servicios: reglas y acceso coordinado a repositorios
----------------------------------------------------
En cada servicio, listar() consulta colecciones y filtros; buscarPorId()
recupera un registro; crear()/actualizar() aplican reglas y mapeos;
eliminar() valida relaciones antes de borrar. obtener() es un auxiliar
privado de busqueda que genera el error de recurso no encontrado.

backend/src/main/java/com/cesde/sidcudb/service/CarreraService.java
- listar(area, nivel), buscarPorId(id), crear(dto), actualizar(id, dto),
  eliminar(id): gestion de carreras.
- obtener(id): busqueda obligatoria; aplicar(carrera, dto): asigna campos;
  resolverHabilidades(ids): busca y verifica habilidades asociadas.

backend/src/main/java/com/cesde/sidcudb/service/EstudianteService.java
- listar(documento, ciudad), buscarPorId(id), crear(dto), actualizar(id,
  dto), eliminar(id): gestion de estudiantes.
- recomendarUniversidades(estudianteId): recomienda instituciones de
  acuerdo con intereses y ciudad.
- obtener(id): recupera el estudiante o informa que no existe.

backend/src/main/java/com/cesde/sidcudb/service/HabilidadService.java
- listar(), buscarPorId(id), crear(dto), actualizar(id, dto),
  eliminar(id): gestion de habilidades; obtener(id): busqueda obligatoria.

backend/src/main/java/com/cesde/sidcudb/service/UniversidadService.java
- listar(ciudad, nombre), buscarPorId(id), crear(dto), actualizar(id,
  dto), eliminar(id): gestion de universidades y sus validaciones.
- obtener(id): busqueda obligatoria.

backend/src/main/java/com/cesde/sidcudb/service/PerfilEstudianteService.java
- listar(estudianteId), buscarPorId(id), crear(dto), actualizar(id, dto),
  eliminar(id): gestion de perfiles y regla de un perfil por estudiante.
- obtener(id): busqueda obligatoria.

backend/src/main/java/com/cesde/sidcudb/service/InteresService.java
- listar(estudianteId, carreraId), buscarPorId(estudianteId, carreraId),
  crear(dto), eliminar(estudianteId, carreraId): administra intereses y
  valida el limite de carreras por estudiante.
- obtener(idCompuesto): recupera la relacion o genera error.

backend/src/main/java/com/cesde/sidcudb/service/InteresUniversidadService.java
- listar(estudianteId, universidadId),
  buscarPorId(estudianteId, universidadId), crear(dto),
  eliminar(estudianteId, universidadId): administra intereses en
  universidades y verifica coherencia con las carreras de interes.
- obtener(idCompuesto): recupera la relacion o genera error.

backend/src/main/java/com/cesde/sidcudb/service/UniversidadCarreraService.java
- listar(universidadId, carreraId),
  buscarPorId(universidadId, carreraId), crear(dto),
  eliminar(universidadId, carreraId): administra la oferta academica y
  evita duplicados.
- obtener(idCompuesto): recupera la relacion o genera error.

--------------------
Todos los repositorios extienden JpaRepository y heredan operaciones
estandar de persistencia/consulta. No declaran consultas personalizadas.

backend/src/main/java/com/cesde/sidcudb/repository/CarreraRepository.java
- Acceso JPA a Carrera.
backend/src/main/java/com/cesde/sidcudb/repository/EstudianteRepository.java
- Acceso JPA a Estudiante.
backend/src/main/java/com/cesde/sidcudb/repository/HabilidadRepository.java
- Acceso JPA a Habilidad.
backend/src/main/java/com/cesde/sidcudb/repository/InteresRepository.java
- Acceso JPA a Interes mediante InteresId.
backend/src/main/java/com/cesde/sidcudb/repository/InteresUniversidadRepository.java
- Acceso JPA a InteresUniversidad mediante InteresUniversidadId.
backend/src/main/java/com/cesde/sidcudb/repository/PerfilEstudianteRepository.java
- Acceso JPA a PerfilEstudiante.
backend/src/main/java/com/cesde/sidcudb/repository/UniversidadCarreraRepository.java
- Acceso JPA a UniversidadCarrera mediante UniversidadCarreraId.
backend/src/main/java/com/cesde/sidcudb/repository/UniversidadRepository.java
- Acceso JPA a Universidad.

Los mappers convierten DTO y entidades, evitando exponer directamente
entidades internas en la API:
- mapper/CarreraMapper.java: toResponse(carrera).
- mapper/EstudianteMapper.java: toEntity(dto), aplicar(estudiante, dto),
  toResponse(estudiante).
- mapper/HabilidadMapper.java: toEntity(dto), aplicar(habilidad, dto),
  toResponse(habilidad).
- mapper/InteresMapper.java: toResponse(interes).
- mapper/InteresUniversidadMapper.java: toResponse(relacion).
- mapper/PerfilEstudianteMapper.java: toResponse(perfil).
- mapper/UniversidadCarreraMapper.java: toResponse(relacion).
- mapper/UniversidadMapper.java: toEntity(dto), aplicar(universidad, dto),
  toResponse(universidad), toUbicacion(dto) (conversion de ubicacion).

======================================================================
9. EJECUCION LOCAL Y VERIFICACIONES
======================================================================

Requisitos:
- JDK 17 o compatible.
- PostgreSQL disponible y una base configurada.
- Node.js y npm para el frontend.

Backend en Windows PowerShell:
1. Definir DB_URL, DB_USERNAME y DB_PASSWORD en el entorno.
2. Desde backend ejecutar:
   .\mvnw.cmd spring-boot:run
3. Abrir http://localhost:8080/swagger-ui.html o
   http://localhost:8080/actuator/health.

Frontend:
1. Desde frontend ejecutar npm install.
2. Definir VITE_API_URL si el backend no esta en la URL predeterminada.
3. Ejecutar npm run dev.
4. Para verificar codigo, usar npm run lint y npm run build.

El backend permite configurar SEED_ENABLED. La carga inicial solo se
ejecuta si el seeder esta habilitado y los catalogos principales estan
vacios. Verificar la configuracion antes de habilitarla en una base con
datos existentes.

La prueba Java de contexto necesita una base accesible y credenciales
validas; no es una prueba aislada en memoria.

======================================================================
10. PRECAUCIONES Y ALCANCE DE LOS DATOS
======================================================================

- No guardar contrasenas, tokens ni URLs privadas de base de datos en el
  repositorio ni en este archivo. Configurar secretos en Render o en el
  entorno local.
- Login y registro no son un mecanismo de seguridad ni una identidad
  persistida.
- Los cuestionarios son autoevaluaciones orientativas, no diagnósticos
  profesionales.
- Los graficos usan conteos del catalogo recibido y no deben presentarse
  como estadisticas de matrículas, demanda o empleo.
- Los datos que se muestran en produccion dependen de la API, de su base
  PostgreSQL y de las variables de entorno configuradas.
